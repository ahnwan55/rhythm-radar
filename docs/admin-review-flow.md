# 관리자 검수 화면과 승인 흐름

## 1. 목적

이 문서는 리듬레이더 알파 단계의 관리자 화면 범위를 정의합니다. 알파에서는 운영자 1명이 관리자 역할을 맡으며, 관리자 화면은 기기 정보 변경 제보를 검토하고 공개 기체 수를 안전하게 갱신하는 데 집중합니다.

현재 단계에서는 화면과 데이터 흐름만 정리하며, 실제 로그인, DB, 백엔드, 파일 저장, 사진 삭제 작업은 구현하지 않습니다.

## 2. 관리자 원칙

- 알파 관리자 수는 1명입니다.
- 알파 로그인 제공자는 카카오이며, 관리자 계정도 카카오 로그인 계정을 기준으로 식별합니다.
- 관리자 권한은 구현 시 초기 관리자 계정에 `ADMIN` 역할을 부여하는 방식으로 시작합니다.
- 일반 이용자에게 증거 사진을 공개하지 않습니다.
- 증거 사진은 관리자 검수용으로만 열람하고, 접수 시점 기준 2주 뒤 자동 삭제합니다.
- 점포 신규 추가는 알파 관리자 화면에서 처리하지 않고 코드 또는 정적 데이터 갱신으로 처리합니다.

## 3. 화면 범위

| 화면 | 목적 | 알파 포함 |
| --- | --- | --- |
| 변경 제보 목록 | 미처리 기기 정보 변경 제보 확인 | 포함 |
| 변경 제보 상세 | 설명, 사진, 대상 점포/기종, 처리 기록 확인 | 포함 |
| 승인/반려 처리 | 승인 시 공개 기체 수와 참고 정보를 갱신 | 포함 |
| 신고 목록 | 이상 대기 상태 제보 신고 확인 | 포함 |
| 제보 로그 조회 | 대기 상태 제보 이력과 반복 제보 확인 | 포함 |
| 점포 신규 등록 | 새 점포를 화면에서 추가 | 제외 |
| 점주용 관리 화면 | 점포 운영자가 직접 수정 | 제외 |

## 4. 변경 제보 목록

목록에서는 관리자가 처리해야 할 `MachineChangeReport`를 빠르게 확인합니다.

| 항목 | 표시 |
| --- | --- |
| 접수 시각 | 상대 시간 또는 절대 시각 |
| 점포/기종 | 변경 대상 |
| 변경 유형 | `BROKEN`, `REPAIRED`, `ADDED`, `REMOVED`, `OTHER` |
| 처리 상태 | `PENDING`, `APPROVED`, `REJECTED` |
| 사진 보관 만료 | `retention_until` |

기본 정렬은 `PENDING` 상태를 먼저, 그 안에서는 오래된 접수 건을 먼저 보여 줍니다.

## 5. 변경 제보 상세

상세 화면은 관리자만 접근할 수 있습니다.

| 영역 | 표시 |
| --- | --- |
| 제보 내용 | 이용자가 작성한 설명과 변경 유형 |
| 현재 공개값 | `totalMachineCount`, `trackedMachineCount`, `activeTrackedMachineCount`, `untrackedMachineCount` |
| 기체/버전 그룹 | `machineGroups`의 모델, 버전, 추적 여부, 가동 수 |
| 증거 사진 | 관리자 전용 열람 |
| 처리 입력 | 승인/반려, 변경 후 수치, 처리 메모 |

사진은 공개 페이지, 제보자 외 이용자 화면, 점포 상세 화면에 노출하지 않습니다.

## 6. 승인 처리

승인 시 관리자는 공개값을 직접 확정합니다.

1. 제보 대상 점포-기종과 현재 공개값을 확인합니다.
2. 사진과 설명을 보고 변경 유형을 판단합니다.
3. 필요한 경우 `MachineGroup`의 `machine_count`, `active_machine_count`, `service_status`, `is_queue_tracked`, `note`를 갱신합니다.
4. `StoreGame`의 네 가지 기체 수를 재계산합니다.
5. `MachineCountRevision`을 생성합니다.
6. `MachineChangeReport.review_status`를 `APPROVED`로 바꾸고 `reviewed_by`, `reviewed_at`을 기록합니다.

승인된 사진 자체는 공개 근거로 보여 주지 않습니다. 공개 화면에는 승인 후 기체 수와 참고 메모만 반영합니다.

## 7. 반려 처리

반려는 다음 경우에 사용합니다.

- 사진으로 기체 수, 버전, 가동 상태를 판단할 수 없음
- 대상 점포 또는 기종이 잘못됨
- 동일한 내용이 이미 반영됨
- 사진에 개인정보 노출이 커서 검수 자료로 쓰기 어려움
- 장난 또는 악성 제보로 판단됨

반려 시 공개 기체 수는 변경하지 않습니다. 반려 사유는 운영 로그에 남기되, 이용자에게 노출할 문구는 짧고 안전하게 유지합니다.

## 8. 사진 보관과 삭제

- `EvidencePhoto.created_at` 기준 14일 뒤 `retention_until`을 설정합니다.
- `retention_until`이 지난 사진은 자동 삭제 대상입니다.
- 사진 삭제 후에도 `MachineChangeReport`, `MachineCountRevision`, 처리 메모는 남길 수 있습니다.
- 사진 저장 위치, 파일명, 접근 토큰, 외부 저장소 키 같은 보안 정보는 코드 저장소에 커밋하지 않습니다.

## 9. 신고 검토

관리자는 신고 목록에서 이상 대기 상태 제보를 확인합니다.

| 항목 | 표시 |
| --- | --- |
| 신고 대상 | 점포, 기종, `queueLevel`, 제보 시각 |
| 신고 사유 | `WRONG_QUEUE_LEVEL`, `SPAM_OR_TROLLING`, `WRONG_TARGET`, `OTHER` |
| 신고자 설명 | 선택 입력 설명 |
| 주변 제보 | 같은 점포-기종의 최근 제보 이력 |
| 처리 상태 | `PENDING`, `RESOLVED`, `REJECTED` |

처리 선택:

- `유지`: 신고를 반려하고 대상 제보를 계속 사용합니다.
- `숨김`: 대상 `WaitReport.moderation_status`를 `HIDDEN`으로 바꾸고 최신 상태 계산에서 제외합니다.
- `메모`: 운영상 참고만 남기고 공개 상태는 바꾸지 않습니다.

신고 수만으로 제보를 자동 숨기지 않습니다. 알파에서는 관리자 1명이 신고 내용을 보고 직접 판단합니다.

## 10. 제보 로그 조회

관리자는 알파 운영 중 다음 로그를 확인할 수 있어야 합니다.

| 로그 | 확인 목적 |
| --- | --- |
| `WaitReport` | 반복 제보, 만료 상태, 최근 제보 공백 확인 |
| `Report` | 신고 접수, 처리 상태, 반복 신고 확인 |
| `MachineChangeReport` | 미처리 사진 제보와 처리 결과 확인 |
| `MachineCountRevision` | 공개 기체 수 변경 이력 확인 |

알파에서는 자동 제재를 도입하지 않습니다. 반복 허위 제보가 보이면 관리자 판단으로 제보 숨김, 계정 제한, 후속 정책 추가를 검토합니다.

일일 운영 점검 항목은 [alpha-operations-checklist.md](alpha-operations-checklist.md)를 따릅니다. 특히 제보 공백, 신고 미처리, 사진 자동 삭제 실패, 이력 누락은 매일 확인합니다.

## 11. 후속 결정 사항

- 초기 관리자 계정에 `ADMIN` 역할을 부여하는 구현 방식
- 사진 개인정보 노출 안내 문구
- 사진 자동 삭제 실패 시 관리자에게 알리는 방식
- 신고 남용을 제한할 쿨타임 또는 일일 제한
