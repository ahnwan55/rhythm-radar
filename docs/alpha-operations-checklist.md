# 알파 운영 점검표

## 1. 목적

이 문서는 리듬레이더 알파 운영자가 매일 확인할 최소 점검 항목을 정리합니다. 알파 운영의 목표는 모든 문제를 자동으로 해결하는 것이 아니라, 제보 흐름이 깨졌거나 신뢰도가 떨어지는 상황을 빠르게 발견하고 수동으로 대응하는 것입니다.

현재 단계에서는 운영 루틴만 정의하며, 실제 관리자 화면, DB, 백엔드, 알림, 자동 점검 작업은 구현하지 않습니다.

## 2. 일일 점검 항목

| 점검 항목 | 확인할 내용 | 기본 조치 |
| --- | --- | --- |
| 제보 미반영 | `WaitReport`가 생성됐지만 최신 상태 화면에 반영되지 않은 건 | 만료, 숨김, 쿨타임, 최신 상태 선택 로직을 확인 |
| 제보 공백 | 주요 점포/기종에 30분 이내 유효 제보가 없는 시간대 | `UNKNOWN` 비율을 기록하고 알파 참여 부족인지 장애인지 구분 |
| 신고 미처리 | `Report.status = PENDING`인 신고 | 대상 제보를 유지하거나 `HIDDEN` 처리 |
| 자동 삭제 실패 | `EvidencePhoto.retention_until`이 지났는데 파일이 남은 건 | 수동 삭제 후 삭제 실패 원인 기록 |
| 이력 누락 | 제보, 신고, 기기 변경, 기체 수 변경, 관리자 조치 이력이 빠진 건 | 누락된 처리 흐름을 기록하고 구현 이슈로 전환 |
| 오류/실패 로그 | 저장 실패, 반영 실패, 삭제 실패, 권한 오류 | 재현 가능 여부와 영향 범위를 기록 |

## 3. 제보 공백 판단

제보 공백은 특정 점포-기종에 대해 유효한 대기 상태 제보가 없는 상태입니다. 알파에서는 대기 상태 제보의 유효 시간이 30분이므로, 마지막 유효 제보가 30분을 넘기면 공백으로 봅니다.

제보 공백은 항상 장애를 뜻하지 않습니다.

| 원인 후보 | 판단 기준 |
| --- | --- |
| 이용자 참여 부족 | 특정 기종만 장시간 `UNKNOWN`이고 오류 로그가 없음 |
| 방문 수요 부족 | 낮은 수요 기종에서 반복적으로 공백이 발생 |
| 화면 또는 저장 오류 | 제보 시도는 있는데 `WaitReport` 생성이 없음 |
| 최신 상태 반영 오류 | `WaitReport`는 있는데 화면이 갱신되지 않음 |
| 관리자 숨김 영향 | 최근 제보가 `HIDDEN` 처리되어 유효 제보가 사라짐 |

공백 자체는 숨기지 않습니다. 공개 화면에서는 `확인 필요`, `정보 부족`, 만료된 경우 회색 계열의 `n분 전 제보` 보조 문구로 표시합니다.

## 4. 미반영 제보 확인

제보 미반영은 이용자가 제출한 대기 상태 제보가 최신 상태 계산에 예상대로 반영되지 않은 경우입니다.

확인 순서:

1. `WaitReport`가 실제로 생성됐는지 확인합니다.
2. `created_at`, `expires_at`, `moderation_status`를 확인합니다.
3. 같은 점포-기종의 더 최신 유효 제보가 있는지 확인합니다.
4. 대상 제보가 신고 검토로 `HIDDEN` 처리됐는지 확인합니다.
5. 화면 캐시 또는 최신 상태 선택 로직 문제인지 확인합니다.

정책상 제외된 제보라면 오류가 아닙니다. 예를 들어 30분 만료, 관리자 숨김, 더 최신 제보 존재는 정상 제외 사유입니다.

## 5. 신고 확인

매일 `PENDING` 신고를 확인합니다.

| 처리 | 기준 |
| --- | --- |
| 유지 | 신고 내용만으로 이상 제보라고 보기 어려움 |
| 숨김 | 현장 맥락, 반복 제보, 주변 제보와 비교했을 때 명확히 이상함 |
| 메모 | 즉시 판단하기 어렵지만 추후 반복 여부를 볼 필요가 있음 |

알파에서는 신고 수만으로 자동 숨김 처리하지 않습니다. 관리자가 직접 확인한 뒤 `WaitReport.moderation_status`를 유지하거나 `HIDDEN`으로 바꿉니다.

## 6. 자동 삭제 확인

증거 사진은 접수 시점 기준 2주 뒤 자동 삭제되어야 합니다.

확인할 항목:

- `retention_until`이 지난 `EvidencePhoto`가 남아 있는지
- 사진 파일은 삭제됐지만 메타데이터와 처리 이력은 남아 있는지
- 자동 삭제 실패 로그가 있는지
- 실패가 반복되는 저장소나 파일 경로가 있는지

사진은 공개 화면에 노출하지 않으며, 삭제 실패는 개인정보 리스크가 있으므로 우선순위를 높게 둡니다.

## 7. 이력 확인

다음 이력이 남아 있어야 합니다.

| 이력 | 확인 이유 |
| --- | --- |
| `WaitReport` | 표시된 대기 상태의 근거 확인 |
| `Report` | 이상 제보 신고와 처리 흐름 확인 |
| `MachineChangeReport` | 기기 정보 변경 제보 접수 확인 |
| `MachineCountRevision` | 공개 기체 수가 바뀐 이유 확인 |
| 관리자 조치 로그 | 제보 숨김, 신고 반려, 승인/반려 책임 추적 |
| 사진 삭제 로그 | 자동 삭제 성공/실패 확인 |

운영자가 나중에 “왜 이 값이 이렇게 됐지?”를 추적할 수 있으면 충분합니다. 알파에서는 과도한 분석 대시보드보다 이력 누락 방지가 우선입니다.

## 8. 주간 회고 항목

매일 점검 결과를 모아 주 1회 다음 항목을 확인합니다.

- 제보 공백이 많은 점포/기종
- 신고가 반복되는 점포/기종
- 자동 삭제 실패 재발 여부
- 기기 정보 변경 제보 처리 부담
- 쿨타임이 너무 빡빡하거나 느슨한지
- 알파 1차 점포 범위가 운영 가능한지

주간 회고 결과는 후속 정책 조정이나 구현 이슈 분리에 사용합니다.
